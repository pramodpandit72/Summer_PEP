# Redis Caching and Message Queues

---

# Redis Caching

## What is Redis?

Redis (**RE**mote **DI**ctionary **S**erver) is an **in-memory NoSQL database** used for:

- Caching
- Session Storage
- Real-time Applications
- Message Brokering
- Pub/Sub Messaging

Redis stores data in **RAM (Memory)**, making it much faster than traditional databases.

---

# Why Use Redis?

Without Redis:

- Every request goes to the database.
- Database becomes overloaded.
- Response time increases.

With Redis:

- Frequently used data is stored in memory.
- Data is retrieved much faster.
- Database load is reduced.

---

# What is Caching?

Caching is the process of storing frequently accessed data in a temporary storage area (cache) so it can be retrieved quickly.

Instead of reading data from the database every time, the application first checks the cache.

---

# Caching Flow

```
Client
   |
Request
   |
Application
   |
Check Redis Cache
   |
-------------------------
|                       |
Data Found          Data Not Found
(Cache Hit)         (Cache Miss)
|                       |
Return Data         Fetch from Database
                        |
                  Store in Redis
                        |
                  Return Data
```

---

# Cache Hit

A **Cache Hit** occurs when the requested data is already available in Redis.

Example:

```
User Profile
↓

Redis

↓

Return Data
```

Response is very fast.

---

# Cache Miss

A **Cache Miss** occurs when the requested data is not available in Redis.

Flow:

```
Request

↓

Database

↓

Store in Redis

↓

Return Data
```

Future requests will use the cached data.

---

# Benefits of Redis Caching

- Very fast data access
- Reduces database load
- Improves application performance
- Supports millions of requests
- Better user experience

# Redis Expiration (TTL)

Redis allows data to expire automatically after a specified time.

TTL stands for **Time To Live**.

Example:

```
User Session

Expires after 30 minutes
```

Benefits:

- Removes outdated data automatically
- Saves memory
- Keeps cache fresh

# What is a Message Queue?

A Message Queue is a communication system that allows applications or services to exchange messages asynchronously.

Instead of communicating directly, services send messages to a queue.

Other services read messages from the queue when they are ready.

---

# Why Use Message Queues?

Without Message Queue:

```
Order Service

↓

Payment Service

↓

Notification Service

↓

Inventory Service
```

If one service becomes slow, the entire process slows down.

---

With Message Queue:

```
Order Service

↓

Message Queue

↓

Payment Service

↓

Notification Service

↓

Inventory Service
```

Each service processes messages independently.

---

# Message Queue Architecture

```
Producer
    |
Send Message
    |
Message Queue
    |
Receive Message
    |
Consumer
```

---

# Components of a Message Queue

## 1. Producer

The producer sends messages to the queue.

Example:

Order Service

Creates:

```
Order Created
```

---

## 2. Message Queue

Stores messages until they are processed.

Acts as a temporary storage between services.

---

## 3. Consumer

The consumer reads messages from the queue and performs the required task.

Example:

Notification Service

Reads:

```
Order Created
```

Sends confirmation email.

---

# Message Queue Flow

```
User Places Order
        |
        v
Order Service
        |
Creates Message
        |
        v
Message Queue
        |
-------------------------
|          |            |
Payment Inventory Notification
Service   Service      Service
```

Each consumer processes the message independently.

---

# Synchronous vs Asynchronous Communication

| Synchronous | Asynchronous |
|-------------|--------------|
| Waits for response | Does not wait for response |
| Direct communication | Uses message queue |
| Higher dependency | Loosely coupled |
| Slower for long tasks | Better for background processing |

---

# Advantages of Message Queues

---

# Redis as a Message Broker

Redis can also be used for messaging through **Pub/Sub (Publish/Subscribe)**.

Example:

Publisher

```
New Product Added
```

Subscribers:

- Notification Service
- Search Service
- Recommendation Service

Each subscriber receives the event.

---

# Redis Pub/Sub Flow

```
Publisher
     |
Publish Event
     |
Redis Channel
     |
-----------------------
|         |           |
Subscriber Subscriber Subscriber
```

# Best Practices

## Redis

- Cache frequently accessed data.
- Set TTL for cached data.
- Avoid storing unnecessary data.
- Use meaningful key names.
- Monitor memory usage.

---

## Message Queues

- Keep messages small.
- Handle duplicate messages safely.
- Monitor queue length.
- Retry failed messages.
- Use acknowledgements to ensure message delivery.

## Q3. What is the difference between a Cache Hit and a Cache Miss?

**Answer:**

- **Cache Hit:** The requested data is found in Redis and returned immediately.
- **Cache Miss:** The requested data is not found in Redis, so it is fetched from the database, stored in Redis, and then returned.
